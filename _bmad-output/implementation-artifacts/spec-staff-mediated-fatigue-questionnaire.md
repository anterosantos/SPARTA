## Intent

**Problem:** Jogadores sem acesso ao telemóvel durante o treino não conseguem responder ao questionário de fadiga pré/pós-sessão — hoje só o próprio jogador autenticado o pode preencher.

**Approach:** No painel de Prontidão, um novo botão "Questionários Jogadores" abre uma lista de jogadores da(s) equipa(s) do treinador, cada um com botões "Pré" e "Pós" que abrem o questionário de fadiga desse jogador nessa sessão — reutilizando o componente `<FatigueQuestionnaire>` existente, com um novo caminho de submissão para staff.

## Boundaries & Constraints

**Always:**
- Autorização: `requireStaffRole()` (coach/analyst) + jogador-alvo tem de pertencer ao âmbito de equipas do staff (`getPlayerIdsForTeams`) — mesmo padrão de `readiness.ts`.
- `<FatigueQuestionnaire>` reutilizado sem alterar o seu comportamento self-serve: apenas duas novas props opcionais (`mode?: "self"|"staff"`, default `"self"`; `redirectOnDismiss?: string`, default `"/hoje"`) — chamadas existentes continuam a funcionar sem alterações.
- Em `mode="staff"`: esconder o toggle "Vai faltar" e não chamar `declarePlayerAbsence`/`cancelPlayerAbsence`; chamar `submitFatigueResponseByStaff` em vez de `submitFatigueResponse`; sem submissão offline via outbox — se `!navigator.onLine`, mostrar erro claro em vez de enfileirar.
- Extrair a lógica pós-escrita de `submitFatigueResponse` (upsert `fatigue_responses`, transição de presença, `session_metrics`, audit log, refresh de snapshot) para um helper interno partilhado; a autorização/validação do caminho self-serve (passos 1-5: Zod, auth, resolução do próprio jogador, `player_id` tem de ser o próprio, `processing_restricted`) mantém-se comportamentalmente idêntica.
- **Reenvio/edição de resposta já existente (jogador OU staff):** o upsert em `fatigue_responses` tem de ter como alvo de conflito a chave real `UNIQUE(player_id, session_id, phase)` (constraint `fatigue_responses_unique_phase`, `supabase/migrations/000200_fatigue_responses.sql`) — não o `id` gerado no cliente. Isto vale tanto para `submitFatigueResponse` como para `submitFatigueResponseByStaff` (via o helper partilhado). Reenviar um questionário já respondido deve **atualizar a linha existente**, nunca falhar com erro de constraint nem criar uma segunda linha.
- Quando o treinador reabre uma fase já respondida (indicador ✓ na lista), a página host busca a resposta existente (`fatigue_responses` filtrado por `player_id, session_id, phase`) e passa os valores para pré-preencher o formulário. Submeter atualiza essa mesma linha, **sem diálogo de confirmação** (consistente com a decisão de não ter fricção extra para este dado reversível de baixo risco).
- Transição de presença (`sem_questionario` → `present`) dentro do helper partilhado só corre quando `via === "self"` — uma submissão em modo staff nunca altera o estado de presença (ausência é gerida exclusivamente via o ecrã de presenças existente).
- A fase `post` em modo staff aplica a mesma guarda que o self-serve: se o jogador estiver marcado `absent` nessa sessão (`getPlayerAttendanceForSession`/query equivalente), a página host mostra a mesma mensagem de erro do fluxo self-serve em vez do formulário.
- `submitFatigueResponseByStaff` aplica a guarda `requiresFatigueQuestionnaire(session.type)` como defesa em profundidade — não confiar apenas na guarda das páginas (padrão #16 de `AGENTS.md`: comportamento condicional por tipo de sessão exige guarda em todos os pontos de entrada, incluindo a ação de escrita).
- Audit log distingue autoria: `actor_id` = utilizador staff autenticado, `target_id` = jogador, `payload.via = 'staff'` (mesma convenção de `withdrawConsentByStaff`).
- Novas rotas sob `(staff)` — nunca reaproveitar a rota `/questionario/[sessionId]/[phase]` existente (assume sempre `profile_id = auth.uid()`).

**Ask First:** Se a lista de jogadores no ecrã de entrada deve incluir jogadores fora das equipas atribuídas ao treinador — assumir que não (mesmo âmbito de `getPlayerIdsForTeams` já usado em Prontidão), salvo indicação em contrário.

**Never:** Nova coluna em `fatigue_responses` para registar autoria (usa apenas `audit_logs`); suporte offline/outbox no caminho staff; alterar validação/controlo do caminho self-serve existente (passos 1-5 de `submitFatigueResponse`); bloquear reenvio de um jogador já respondido; diálogo de confirmação antes de submeter (em nenhum dos dois modos).

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Jogador no âmbito, nunca respondeu | Staff clica "Pré" para jogador da sua equipa | Abre formulário pré-treino vazio para esse jogador | N/A |
| Jogador já respondeu a essa fase | Staff clica "Pré ✓"/"Pós ✓" na lista | Formulário abre pré-preenchido com a resposta existente; submeter atualiza a mesma linha (upsert na chave real) | N/A |
| Jogador fora do âmbito do staff | URL directa com `playerId` de outra equipa/clube | Acesso negado | `not_found`, sem revelar existência do recurso |
| Sessão é Palestra/Médico/Outros | Staff abre lista de questionários para essa sessão, OU chama a ação de escrita directamente | Mensagem "Esta sessão não tem questionário de fadiga" (lista/página); ação de escrita rejeita com erro equivalente | Guarda `requiresFatigueQuestionnaire` na lista, na página host, E na ação de escrita |
| Jogador marcado ausente, staff tenta fase `post` | Staff clica "Pós" para jogador com `attendance.status === 'absent'` nessa sessão | Mesma mensagem de erro do fluxo self-serve, formulário não é mostrado | N/A |
| Staff sem rede ao submeter | Clica "Submeter" com `navigator.onLine === false` | Erro claro, nada é gravado nem enfileirado | Mensagem de erro inline |

**Acceptance Criteria:**
- Given um treinador autenticado com sessão futura em `/prontidao`, when clica "Questionários Jogadores", then vê a lista de jogadores das suas equipas com botões "Pré" e "Pós".
- Given a lista de jogadores, when o treinador clica "Pré" para um jogador, then abre o questionário pré-treino desse jogador específico (não o do próprio treinador).
- Given um jogador que já respondeu à fase pré, when o treinador clica "Pré ✓" e reenvia, then a linha existente em `fatigue_responses` é atualizada (mesmo `player_id+session_id+phase`), sem erro de constraint e sem duplicar.
- Given um jogador marcado ausente nessa sessão, when o treinador tenta abrir a fase `post` para esse jogador, then vê a mesma mensagem de bloqueio do fluxo self-serve.
- Given o treinador submete um questionário em nome de um jogador, when consulta `audit_logs`, then a entrada tem `actor_id` do treinador, `target_id` do jogador e `payload.via = 'staff'`; e a presença do jogador não é alterada por essa submissão.
- Given uma sessão do tipo Palestra, when o treinador abre a lista de questionários dessa sessão OU tenta chamar `submitFatigueResponseByStaff` directamente para essa sessão, then ambos rejeitam/bloqueiam de forma equivalente.
- Given uma sessão `cancelled`, when o treinador tenta abrir ou submeter um questionário (página ou ação directamente), then é bloqueado com a mesma guarda do self-serve, tanto na página como na ação de escrita.
- Given um jogador com `processing_restricted = true`, when o treinador reabre uma fase já respondida desse jogador, then vê um erro claro antes de qualquer dado de bem-estar ser mostrado ou pré-preenchido, não só no submit final.
- Given um draft local antigo em IndexedDB para o mesmo `sessionId:phase:playerId`, when o treinador reabre uma fase já respondida na base de dados, then o formulário mostra a resposta real da base de dados, não o draft desatualizado.
- Given o fluxo self-serve do próprio jogador em `/questionario/[sessionId]/[phase]`, when um jogador submete o seu próprio questionário após esta mudança, then o comportamento é idêntico ao anterior (sem regressão).

## Design Notes

**Porquê extrair um helper em vez de duplicar `submitFatigueResponse`:** seguindo a convenção de `spec-staff-mediated-consent-withdrawal.md` ("a variante staff é uma ação paralela que chama a mesma primitiva partilhada no fim, não uma versão modificada da self-serve"), evita risco de regressão no caminho self-serve já testado, enquanto elimina duplicação dos efeitos secundários.

**Porquê upsert na chave real em vez de `id`:** o `id` é gerado no cliente a cada carregamento de página (UUIDv7), pelo que nunca coincide entre duas submissões distintas para o mesmo jogador/sessão/fase — o `onConflict` tem de apontar para a constraint que realmente identifica "a resposta desta fase, desta sessão, deste jogador" (`fatigue_responses_unique_phase`), não para a chave primária técnica.

**Sem confirmação pesada:** ao contrário da retirada de consentimento (RGPD, irreversível), submeter ou corrigir um questionário de fadiga é uma ação reversível e de baixo risco (dado de bem-estar subjetivo, não legal) — tanto a submissão inicial como a edição de uma resposta existente seguem o mesmo fluxo direto, sem confirmação adicional.
